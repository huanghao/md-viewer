# 文档治理规范

## 核心原则：内容活性

**文档的存在理由是"当前有人会读它"，而不是"当时写了它"。**

腐烂的文档比没有文档更危险——它误导 agent 和未来的自己。每隔一段时间问自己：这个文档描述的还是现实吗？答不上来就删。

## 1. 文档分层

| 层级 | 目录/文件 | 说明 |
|------|-----------|------|
| 项目入口 | `README.md`、`AGENTS.md` | 长期维护，必须与现实同步 |
| 文档入口 | `docs/README.md` | docs 的唯一总索引 |
| 治理规范 | `docs/文档治理规范.md` | 文档保留、删除、命名和巡检规则 |
| 设计真相源 | `docs/design/` | 架构语义、状态模型、核心交互约束 |
| 参考文档 | `docs/reference/` | 运行手册、专题机制说明、发布检查 |
| 测试文档 | `docs/testing/` | 手工测试、测试计划、测试故事 |

`docs/` 根目录只放总索引和治理规范，不再堆专题文档。

## 2. 删除优先于保留

不再准确的文档直接删，不迁移、不归档。**重复内容**只保留一份权威位置，其他地方引用而不复制。

不新增这些目录：
- `docs/archive/`：历史记录交给 git。
- `docs/research/`：阶段性调研如果没有长期复用价值，完成后删除；有价值则整理进 `design/` 或 `reference/`。
- `docs/design/<topic>/` 原型素材目录：长期文档不保留 HTML/SVG/PNG 原型，除非该资产仍被产品或测试直接使用。

## 3. 单一事实源

同一主题只保留 1 份权威文档，其他地方只引用，不复制参数表、状态规则、流程描述。

## 4. 文档命名

- 权威文档优先使用稳定文件名，必要时可保留历史日期前缀。
- 新增长期设计文档放 `docs/design/`，文件名必须能表达主题。
- 新增运行/专题参考放 `docs/reference/`。
- 新增测试说明放 `docs/testing/`。
- 不新增纯原型 HTML、截图素材、一次性计划文档；需要临时记录时写在任务分支或 issue/PR，落地后删除。

## 5. 变更同步

CLI 参数或配置行为变化时，同步更新：
- `showHelp()` 输出（真相源）
- 对应的设计文档（如有）

涉及下面内容时必须同步更新对应文档：
- 状态语义、badge 规则、workspace/session 边界：`docs/design/*state*`
- PDF 渲染、选区、批注机制：`docs/reference/pdf-*` 或 `docs/design/20260419-pdf-annotation-flow.md`
- 评论存储/锚点：`docs/design/20260304-annotation-storage-and-anchoring.md`
- 发布流程：`docs/reference/release-checklist.md`

## 6. 巡检清单

```
[ ] 有没有描述已不存在的功能/流程的文档？→ 删除
[ ] 有没有重复描述同一件事的文档？→ 合并或删除副本
[ ] docs/README.md 的索引是否还准确？→ 更新
[ ] docs/design/README.md 和 docs/reference/README.md 是否还准确？→ 更新
[ ] AGENTS.md 引用的文件是否都存在？→ 修正
[ ] 是否新增了 archive/research/prototype 类目录？→ 删除或整理进长期文档
```
